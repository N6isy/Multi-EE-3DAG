> 最新入口：docs/README.md、training/README.md、五任务训练初版结果进度汇报.md。

更新时间：2026-06-16

## 为什么 executor 不能只作为类别 ID

只用 `gripper / suction / hook / dexterous_hand` 这四个类别 ID，模型能知道“这是第几个执行器”，但不知道“这个执行器为什么适合某些几何区域”。例如 suction 需要平整接触面，hook 更依赖边缘、孔洞或可勾住结构，gripper 关注两侧可夹持区域，dexterous hand 更像多接触点包络。

类别 ID 对当前四类执行器够用，但它把所有机制差异都压进一个离散 token。这样会带来两个问题：

1. 很难解释模型到底学到了什么执行器规律。
2. 未来加入新执行器时，只有一个新 ID，模型无法利用它和已有执行器之间的相似性。

## 四类执行器的机制差异

gripper 主要依赖夹持几何，常见信号是薄边、两侧可接近区域、可形成稳定夹持的局部结构。

suction 主要依赖吸附接触，常见信号是局部平整、接触 patch 足够大、表面法向和可达方向比较稳定。

hook 主要依赖勾挂或拉拽，常见信号是边缘、孔洞、把手内侧、可承受拉力的局部结构。

dexterous_hand 主要依赖多指接触和包络，几何约束更宽，但自由度更高，可能覆盖抓、按、扶、托等动作。

## 属性如何进入模型

当前属性规格文件是：

```text
training/configs/executor_specs_v0_1.json
```

每个 executor 至少包含：

```text
contact_mode
contact_geometry
requires_flatness
requires_edge_or_thin_part
can_hook_inside
can_press
can_pull
can_lift
tip_width_norm
contact_patch_norm
dof_norm
```

数值字段直接作为 0 到 1 的归一化属性。类别字段会在代码中稳定编码成 one-hot，例如 `contact_mode=vacuum`、`contact_geometry=curved_tip`。

模型入口在：

```text
training/executor_conditioning.py
```

支持的条件模式：

```text
learnable_id
one_hot_id
attr_only
id_attr
id_attr_film
id_attr_crossattn
```

第一批建议对比：

```text
pointnext_shared4_5tasks
pointnext_executor_attr_only_5tasks
pointnext_executor_id_attr_5tasks
pointnext_executor_id_attr_film_5tasks
pointnext_executor_id_attr_crossattn_5tasks
```

## FiLM 是什么

FiLM 可以理解成“根据执行器属性调节点特征”。当前实现的公式是：

```text
gamma, beta = executor_attr_mlp(executor_attr)
point_features = point_features * (1 + gamma) + beta
```

也就是说，同一个点云点在 gripper、suction、hook、dexterous hand 下会被不同属性重新加权。平面区域对 suction 可能被增强，薄边或内侧结构对 hook 可能被增强。

## 为什么支持未来新执行器

如果只用类别 ID，新执行器必须从随机 ID 学起。属性条件建模允许新执行器先用属性描述进入模型，例如：

```text
接触方式：vacuum
接触几何：small_patch
需要平整度：0.8
可拉拽：0.4
自由度：0.2
```

这样模型至少能把新执行器放到已有机制空间中，而不是完全陌生的类别。

## 当前实验如何证明有效

有效性不能只看 overall mIoU。建议至少比较：

```text
macro_iou
macro_dice
per_executor_iou
task_executor_iou
macro_feasibility_f1
empty_mask_accuracy
executor_overlap_matrix_error
```

关键对照：

1. `learnable_id` 对比 `one_hot_id`：验证可学习 executor token 是否重要。
2. `learnable_id` 对比 `attr_only`：验证纯属性能否表达执行器差异。
3. `learnable_id` 对比 `id_attr`：验证属性是否给 ID token 带来额外收益。
4. `id_attr` 对比 `id_attr_film`：验证属性调节点特征是否比只调 executor query 更有效。
5. `id_attr_film` 对比 `id_attr_crossattn`：验证更强交互是否值得额外复杂度。

## 哪些可以写进论文

可以写进论文的结论必须来自完整训练和同一评估协议：

```text
属性条件模型是否提升整体和分执行器指标
FiLM 是否改善需要几何机制区分的 executor
新 head 是否保持 feasibility 与 mask 的一致性
```

只能作为分析或消融动机的内容：

```text
人工属性值本身的主观设定
单次 debug run 的 loss 变化
未编译 CUDA extension 前的 PointNeXt 环境失败
```
