# 标注版本冻结与研发分支说明

更新时间：2026-05-26

本文档说明如何把当前轻量自动候选 + 人工点级审查版本固定下来，用于双人协作标注；同时保留一个独立研发分支继续改进自动候选区域生成器。

## 1. 为什么要冻结标注版本

人工标注开始后，候选生成逻辑、候选排序、样本 JSONL 和审查系统行为都需要稳定。如果在标注过程中继续修改候选生成器，容易出现：

- 同一批样本前后候选 ID 不一致；
- 审查者看到的候选区域和服务器中保存的 mask 不一致；
- `v3_candidate_samples_v0_1.jsonl` 与 `candidate_manifest.json` 指向不同版本；
- 已审查数据和新生成数据混在一起，后续难以复现。

因此当前版本先固定为 `annotation/mvp-v0.1`，候选生成器后续优化进入单独研发分支。

## 2. 分支与标签约定

稳定标注版本：

```text
branch: annotation/mvp-v0.1
tag:    annotation-mvp-v0.1
```

候选生成研发版本：

```text
branch: dev/high-recall-candidate-v0.2
```

含义：

- `annotation/mvp-v0.1`：只接受审查系统 bugfix、文档修正和不改变候选语义的轻量修复。
- `annotation-mvp-v0.1`：用于给审查者固定 checkout 的精确版本。
- `dev/high-recall-candidate-v0.2`：用于继续改进候选生成器、规则过滤、VLM 选择提示词和新实验。

## 3. 建议创建流程

在确认当前文档和代码可用后，维护者执行：

```bash
git status --short
git checkout -b annotation/mvp-v0.1
git add MultiEEAffordance/docs .gitignore
git commit -m "docs: add dual reviewer annotation workflow"
git tag annotation-mvp-v0.1
git push -u origin annotation/mvp-v0.1
git push origin annotation-mvp-v0.1
```

如果需要先同步远程 `main`，应在开始编辑文档前执行 `git pull`；如果本地已经有未提交的文档改动，不要直接 `git pull` 覆盖当前工作区，先确认 diff 并完成本次提交。

然后从 `main` 或当前最新研发基线创建候选生成研发分支：

```bash
git checkout main
git pull
git checkout -b dev/high-recall-candidate-v0.2
git push -u origin dev/high-recall-candidate-v0.2
```

如果 `main` 上还有未稳定的自动候选生成改动，则不要把它们混入 `annotation/mvp-v0.1`。标注分支只保留当前能启动审查、能保存 refined mask、能打包 release 的稳定版本。

### 3.1 创建前检查清单

创建稳定标注分支前先确认：

- `serve_v2_annotation_app.py` 能启动；
- `v3_candidate_samples_v0_1.jsonl` 能被审查系统读取；
- 至少一条样本能保存 refined mask；
- `build_reviewed_dataset_release.py` 能读取 refined samples；
- 文档中不再把旧 `ground,project,grow` 写成推荐主线；
- `.gitignore` 已忽略 `processed/annotation_batches/`。

可以用下面命令做轻量检查：

```bash
git status --short
python -m py_compile MultiEEAffordance/tools/serve_v2_annotation_app.py
python -m py_compile MultiEEAffordance/tools/build_reviewed_dataset_release.py
```

如果本地没有完整 Python 环境，至少完成 `git status --short` 和文档检查，再到服务器端运行 py_compile。

## 4. 标注期间允许的改动

可以进入 `annotation/mvp-v0.1` 的改动：

- README 和操作说明修正；
- 审查网页无法保存、无法打开样本这类 bugfix；
- 不改变候选 ID、候选 mask、样本划分和输出格式的 UI 小修；
- reviewed dataset 打包脚本的非破坏性修复。

不建议进入 `annotation/mvp-v0.1` 的改动：

- 改候选生成算法；
- 改 VLM 候选选择 prompt；
- 改规则过滤阈值；
- 重新生成同名 `v3_candidate_samples_v0_1.jsonl`；
- 在同一批次中改变候选排序或默认勾选策略。

如果确实需要改变候选生成逻辑，应生成下一批版本，例如 `annotation/mvp-v0.2`，并重新生成候选队列和人工审查批次。

### 4.1 稳定分支 hotfix 流程

如果标注期间审查系统出现必须修复的问题，例如保存失败、pending 样本打不开，可以在稳定分支上做 hotfix：

```bash
git checkout annotation/mvp-v0.1
git pull
# 修改代码或文档
python -m py_compile MultiEEAffordance/tools/serve_v2_annotation_app.py
git add <changed_files>
git commit -m "fix: stabilize annotation app save flow"
git push
```

hotfix 原则：

- 只修复阻塞标注的问题；
- 不改变候选生成结果；
- 不重排候选 ID；
- 不覆盖现有 refined mask；
- 修改后通知两位审查者刷新页面或重启各自服务。

如果改动会影响候选生成或默认正例，应进入研发分支，而不是 hotfix 到标注分支。

## 5. 数据和 Git 的边界

Git 管理：

- 代码；
- README；
- 小型 metadata 示例；
- 文档和运行说明。

服务器目录管理：

- 原始点云；
- VLM 渲染图；
- candidate manifest / candidate masks；
- refined mask `.npy`；
- 人工审查 JSONL；
- reviewed dataset release 产物。

当前双人协作输出统一放在：

```text
MultiEEAffordance/processed/annotation_batches/v0_1/
```

该目录不建议提交到 Git，应按批次备份。

建议批次目录中保留：

```text
BATCH_INFO.md
reviewer_a_samples.jsonl
reviewer_b_samples.jsonl
reviewer_a_review_records.jsonl
reviewer_b_review_records.jsonl
reviewer_a_refined_samples.jsonl
reviewer_b_refined_samples.jsonl
manual_refined_masks_reviewer_a/
manual_refined_masks_reviewer_b/
merged_refined_samples.jsonl
conflict_review.jsonl
```

其中 `conflict_review.jsonl` 只记录重复或需要二次判断的样本，不直接进入 release。

## 6. 版本切换原则

标注者：

```bash
git checkout annotation/mvp-v0.1
```

维护者继续研发：

```bash
git checkout dev/high-recall-candidate-v0.2
```

如果研发分支产出更好的候选生成器，不要直接覆盖 v0.1 标注批次。应先跑小批测试，确认稳定后创建新的候选和审查批次：

```text
processed/annotation_batches/v0_2/
```

这样 v0.1 的人工审查结果始终可复现，v0.2 的自动候选改进也能独立评估。

## 7. 从 v0.1 升级到 v0.2 的条件

只有满足以下条件时，才建议创建新的标注批次：

- 候选生成器明显提高 recall，例如 handle/button/loop 漏召回显著减少；
- 自动默认正例明显更保守，不再频繁覆盖大主体；
- 小批 20 到 50 条样本验证通过；
- 审查系统兼容旧 refined samples，不破坏 v0.1 产物；
- 新候选结果需要重新人工审查，而不是覆盖 v0.1。

v0.2 推荐目录：

```text
processed/annotation_batches/v0_2/
processed/metadata/v3_candidate_samples_v0_2.jsonl
processed/metadata/reviewed_dataset_v0_2.jsonl
```

不要把 v0.2 refined mask 写入 v0.1 目录。

## 8. 当前推荐执行顺序

维护者视角：

1. 在 `main` 上完成文档和稳定工具修正。
2. 创建 `annotation/mvp-v0.1` 分支并打 `annotation-mvp-v0.1` tag。
3. 在服务器端 checkout `annotation/mvp-v0.1`。
4. 生成或确认 `v3_candidate_samples_v0_1.jsonl`。
5. 按 `object_id` 拆分 `reviewer_a_samples.jsonl` 和 `reviewer_b_samples.jsonl`。
6. 启动两个审查服务。
7. 每天备份 `processed/annotation_batches/v0_1/`。
8. 周期性合并 refined samples，生成 reviewed dataset release。
9. 在 `dev/high-recall-candidate-v0.2` 继续改进候选生成器。

审查者视角：

1. 只使用 `annotation/mvp-v0.1`。
2. 只访问自己端口。
3. 只保存自己的样本。
4. 每天同步审查数量和问题样本。
5. 遇到异常不自行改 pipeline，记录样本并交给维护者处理。
