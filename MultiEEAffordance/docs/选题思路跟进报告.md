# 面向异构末端执行器的多标签 3D 可供性接地研究：选题思路跟进报告

记录日期：2026-05-11 +08:00

本文档用于记录当前选题方向、核心假设、阶段性思路提升、遇到的困难和后续讨论问题。它不是工程进度流水账，而是帮助后续持续判断“这个题是否仍然沿着正确问题前进”的研究备忘录。

## 1. 当前题目

暂定题目：

**面向异构末端执行器的多标签 3D 可供性接地研究**

英文可暂写为：

**Multi-Label 3D Affordance Grounding for Heterogeneous End-Effectors**

当前任务定义：

```text
输入：3D 物体点云 P + 任务指令 q
输出：同一物体、同一任务下，四类末端执行器分别对应的 affordance mask

P, q -> [M_gripper, M_suction, M_hook, M_dexterous_hand]
```

其中：

- `M_gripper`：两指夹爪可操作区域。
- `M_suction`：吸盘可操作区域。
- `M_hook`：钩爪/挂接式执行器可操作区域。
- `M_dexterous_hand`：灵巧手可稳定抓握、包覆、按压或精细操作区域。

核心区别是：当前不是把执行器作为输入条件做 `P, q, e -> M`，而是把输出设计成多通道 mask。模型需要同时判断同一个 object-task 对四类执行器分别哪里可行、哪里不可行。

## 2. 为什么这个题值得做

传统 3D affordance grounding 更常见的形式是：

```text
P, q -> M
```

这类设定通常把“可供性”当作任务相关区域，但较少显式区分不同末端执行器的物理接触差异。实际机器人系统里，同样是 `open_pull` 或 `pick_up`，两指夹爪、吸盘、钩爪、灵巧手对应的可操作区域可能完全不同。

例如：

- 门板对 suction 可能可行，但对 gripper 未必可行。
- 有孔把手对 hook 可行，但普通平面不行。
- 瓶身对 dexterous hand 可行，但不应把所有光滑表面都标成灵巧手正样本。
- 大平面中心适合 suction，但可能是 gripper 的负样本。

因此，多执行器输出不仅是多标签形式变化，而是把“任务语义”和“执行器物理接触方式”显式解耦。这个方向的研究价值在于：让模型不只知道“哪里能完成任务”，还知道“对哪种执行器能完成任务”。

## 3. 当前研究目标边界

当前阶段只做：

- 物体级数据集原型。
- 四类任务：`pick_up`、`lift_carry`、`open_pull`、`press_push`。
- 四类执行器：`gripper`、`suction`、`hook`、`dexterous_hand`。
- 点云格式和四通道 mask 格式固定。
- 弱标签 + 人工审查 + VLM/SAM2 候选精修流程。

当前阶段不做：

- 不做完整室内场景级数据。
- 不接 SceneFun3D 场景级 pipeline。
- 不急于训练模型。
- 不把 VLM 直接当最终逐点标签生成器。
- 不把所有可接触表面都泛化成正样本。

这个边界非常重要。当前最容易跑偏的方向是：数据格式还没稳定，就开始堆模型训练；或者 VLM 刚能出 mask，就把候选区域当作可靠真值。

## 4. 当前数据构建路线

当前数据集原型名：

```text
Multi-EE Affordance Dataset v0.1
```

单条样本包含：

- `object_id`
- `source_dataset`
- `object_category`
- `task`
- `task_instruction`
- `point_cloud_path`
- `multi_channel_mask_path`
- `executor_order = ["gripper", "suction", "hook", "dexterous_hand"]`
- 每个执行器的 feasibility label
- 每个执行器的 label_source
- 不可行时的 negative_reason
- quality flag：`weak / checked / verified`
- split：`train / val / test / contrast_test`

mask 固定为：

```text
[N, 4]

mask[:, 0] = gripper
mask[:, 1] = suction
mask[:, 2] = hook
mask[:, 3] = dexterous_hand
```

当前数据来源优先级：

1. 3D AffordanceNet：提供初始物体级点云和已有 affordance mask。
2. PartNet-Mobility：后续补 drawer、cabinet、door、button、handle 等 articulated object 和部件结构。
3. ShapeNet / Objaverse：后续扩展类别和规模，不是 v0.1 重点。

## 6. 人工审查带来的关键认识

人工审查不是简单的数据清洗，它实际推动了选题定义变清楚。

### 6.1 object-task 过滤比预期重要

61 条样本中，16 条被剔除，其中 `task_mismatch` 是主要问题之一。这说明不能只根据原始 affordance 名称机械展开任务。例如某些大件家具虽然存在局部可接触区域，但不适合 `pick_up` 或 `lift_carry`。

后续需要建立 object-task 先验：

- 哪些类别默认不进入 `pick_up`。
- 哪些类别适合 `open_pull`。
- 哪些类别只适合 `press_push`。
- 哪些任务需要 articulated part 语义支持。

### 6.2 hook 是当前最容易漏标的执行器

hook 的 `add_missing / missing_positive` 最突出。原因是 3D AffordanceNet 原始标签中通常没有显式 hookable 区域。`pull/openable` 也不能直接等价于 hook。

hook 需要识别：

- 把手内孔。
- 拉环。
- 孔洞边界。
- 提手开口。
- 可挂接的环状或闭合结构。

这类结构很依赖几何和部件语义，仅靠原始 affordance mask 不够。

### 6.3 suction 需要尺度和几何约束

人工审查中出现一个关键问题：吸盘到底多大？如果吸盘很小，很多局部平面都可能吸附；如果定义太宽，耳机耳包侧面、连接处、小局部平面都会被标为正样本，标签会变得不稳定。

当前 v0.1 的标准应保持保守：

- 标注面积足够、相对平整、低曲率、法向一致、远离边缘的区域。
- 不标注把手、拉环、细杆、孔洞边界、高曲率小区域。
- 小吸盘极限可行性暂不作为 v0.1 的主标准。

这实际上把 suction 从“理论接触可能”收紧为“数据集中稳定、可重复、可泛化的吸附区域”。

### 6.4 dexterous_hand 不能定义成万能接触

灵巧手最容易被泛化。如果把所有能碰到的表面都标为正样本，`dexterous_hand` 就会失去研究意义。

当前定义应坚持：

- 正样本表示类人多指手能稳定抓握、包覆、按压、旋转或精细操作。
- 普通大平面、没有明确操作意义的接触面不标。
- `press_push` 中按钮、开关、按键可以是正样本。
- `pick_up/lift_carry` 中杯身、瓶身、柄部等可包覆区域可以是正样本。

## 7. 当前思路的几次重要提升

### 7.1 从“单 affordance mask”转向“同一 object-task 的多执行器对比”

一开始容易把问题理解成给不同执行器分别做条件输入。但当前更有研究价值的是输出多通道 mask，因为它强制数据和模型表达同一任务下不同执行器的正负差异。

### 7.2 从“自动弱标签”转向“弱标签 + 人工审查 + refine 队列”

直接把已有 affordance mask 映射到四执行器会产生很多错标、漏标。现在已经明确：弱标签只能作为候选，人工审查用于建立质量边界，refine 队列用于后续重点修正。

### 7.3 从“VLM 直接生成 3D mask”转向“VLM/SAM2 生成候选 2D mask，再回投 3D”

当前不把 VLM 当最终逐点标签生成器，而是让它在多视角图上提出候选区域。SAM2 负责更稳定的 2D 分割，几何投影负责回到点云，人工复核负责最终质量判断。

这条路线比“让大模型直接给 3D mask”更可控，也更容易解释错误来源。

### 7.4 从“本地直接跑所有流程”转向“本地 Codex 开发 + GitHub + 远程服务器运行”

远程服务器不能使用 Codex，因此代码必须支持手动命令行运行、相对路径、配置文件和清晰报错。这一工程约束已经写入项目文档，后续不能再默认依赖本地绝对路径或交互式修代码。

## 8. 当前困难与风险

### 8.1 数据规模仍然很小

当前 checked v0.1 只有 45 条样本，VLM pilot 只有 8 条通道级记录。这足够验证格式和流程，但不足以支撑模型训练结论。

短期目标应该是“证明数据构建方式可行”，而不是声称数据集已经可用于完整训练评估。

### 8.2 多执行器标准仍有主观性

尤其是 suction 尺寸、hook 是否能挂住、dexterous hand 是否稳定操作，都有物理尺度和执行器具体设计差异。当前 taxonomy 必须写得足够明确，否则后续人工标注会漂移。

可能需要引入：

- 执行器抽象尺寸假设。
- 最小接触面积阈值。
- 曲率/法向一致性阈值。
- 对 hook 的孔洞/开口结构定义。
- 对 dexterous hand 的任务相关接触定义。

### 8.3 VLM 可能把语义相关误当物理可行

VLM 可能认为“把手”一定能 hook，或者“平面”一定能 suction。但真实可行性还取决于孔洞、方向、厚度、边缘、曲率和接触面积。

因此 VLM/SAM2 结果只能进入 `candidate` 或 `weak/refine`，不能直接变成 `verified`。

### 8.4 3D AffordanceNet 原始标签与本任务不完全对齐

3D AffordanceNet 的 affordance 是行为/功能导向，不是执行器导向。它可以作为起点，但不能完全决定四执行器标签。后续必须引入 PartNet-Mobility 的部件语义和几何规则，否则 hook/open_pull/button/handle 等样本很难稳定。

### 8.5 容易跑偏成纯工程数据清洗

如果后续只是在修脚本、搬数据、跑可视化，而没有持续提炼“执行器异构性如何改变 3D affordance grounding”，研究贡献会变弱。

需要持续把工程动作绑定到研究问题：

- 这个规则修正是否体现执行器差异？
- 这个样本是否增加了强对比性？
- 这个 VLM 结果是否帮助理解 affordance 的物理边界？
- 这个数据字段是否服务于后续建模或评估？

## 9. 当前可以主张的潜在贡献

如果后续继续推进，论文或课题中可以考虑以下贡献点：

1. **任务设定贡献**：提出面向异构末端执行器的多标签 3D affordance grounding，即 `P, q -> [M_e1, M_e2, ...]`。
2. **数据集贡献**：构建 object-level Multi-EE Affordance Dataset，显式标注同一物体同一任务下不同执行器的可操作区域。
3. **标注流程贡献**：提出已有 affordance mask / 部件标注 + 几何规则 + 人工审查 + VLM/SAM2 候选精修的数据构建 pipeline。
4. **对比样本贡献**：设计 executor contrast samples，用于评估模型是否真正区分 gripper/suction/hook/dexterous hand。
5. **后续模型贡献**：在数据稳定后，可进一步研究多通道输出模型、执行器差异约束、多标签一致性损失或执行器间互斥/重叠关系。

当前最稳的贡献顺序应该是：

```text
先证明问题定义和数据构建合理
再扩充样本和标注质量
最后考虑模型训练与评估
```

## 10. 后续阶段建议

### 阶段 A：跑通 Qwen3-VL + SAM2 pilot

目标：

- 在远程服务器安装依赖。
- 对 8 条 pilot 跑 Qwen3-VL + SAM2。
- 生成 2D mask、回投 3D、融合候选 mask。
- 回到本地网页复核。

判断标准：

- 不是看 VLM 是否一次性完美，而是看它能否减少人工从零画 mask 的负担。
- 重点观察 hook 漏标、suction 过标、dexterous hand 欠标是否得到改善。

### 阶段 B：把 pilot 结果转化成规则改进

目标：

- 总结 VLM/SAM2 在不同执行器上的典型成功和失败。
- 把可靠规律写回几何规则或部件规则。
- 对不可靠结果保留人工复核，不进入 verified。

### 阶段 C：接入 PartNet-Mobility

目标：

- 补 drawer、cabinet、door、button、handle 等 articulated object。
- 用部件语义改善 `open_pull` 和 `press_push`。
- 让 hook、gripper、dexterous hand 对 handle/knob/button 的标签更稳定。

### 阶段 D：扩展数据规模和对比测试集

目标：

- 扩展类别和样本数。
- 构造明确的 contrast_test：
  - suction 正 / gripper 负。
  - hook 正 / suction 负。
  - dexterous hand 正 / suction 负。
  - 同一 object-task 多执行器重叠但边界不同。

### 阶段 E：考虑模型 baseline

只有当数据格式、标注协议和质量控制基本稳定后，再考虑训练：

- 输入：点云 + task instruction。
- 输出：`[N, 4]` 多通道 mask。
- 指标：每通道 IoU/F1、feasibility accuracy、executor contrast consistency。

## 11. 防跑偏检查清单

每次新增规则、脚本或数据时，可以问：

- 是否仍然保持 `P, q -> [M_gripper, M_suction, M_hook, M_dexterous_hand]` 的核心设定？
- 是否把执行器物理差异写进了标签，而不是只写任务语义？
- 是否避免把 VLM 输出直接当真值？
- 是否避免把 dexterous hand 泛化成所有可接触面？
- 是否避免把 suction 泛化成所有局部平面？
- 是否避免把 hook 泛化成所有把手？
- 是否保留了人工审查和质量等级？
- 是否优先构建强对比样本，而不是盲目扩大数量？
- 是否仍然聚焦 object-level，而不是提前扩展到复杂场景级？

## 12. 建议和 ChatGPT 讨论的问题

可以把下面这些问题拿去和 ChatGPT 讨论：

1. 这个题的 novelty 应该如何表述？是“多标签输出设定”，还是“异构执行器物理可行性建模”，还是“数据集构建 pipeline”？
2. `P, q -> [M_gripper, M_suction, M_hook, M_dexterous_hand]` 相比 `P, q, e -> M` 的优势和风险是什么？
3. 当前四类执行器定义是否足够清晰？是否需要为 suction/hook/dexterous hand 引入尺寸和几何阈值？
4. 如何设计 executor contrast_test，才能证明模型真的理解执行器差异？
5. VLM/SAM2 在这个数据构建中应该被定位为“候选标签生成器”还是“弱监督来源”？如何避免论文中被质疑为大模型伪标注？
6. PartNet-Mobility 应该优先补哪些类别和部件，才能最大提升 `open_pull` / `press_push` 的数据质量？
7. 如果未来训练 baseline，应该用多通道独立 BCE，还是加入执行器间关系约束？
8. 哪些实验能证明多执行器输出比单执行器条件输入更有价值？
9. 当前 v0.1 样本很少，如何把它合理表述为 prototype，而不是过度声称 dataset contribution？
10. 如果论文工作量有限，应该优先做数据集、规则 pipeline、VLM 辅助标注，还是模型 baseline？

## 14. 当前一句话总结

当前选题已经从“把已有 affordance mask 映射成四通道”提升为一个更清晰的问题：**如何在同一 object-task 条件下，用稳定的数据协议和可审查的弱标注流程，表达不同末端执行器之间真实的物理可操作差异。**

后续最重要的不是马上训练模型，而是继续把“执行器差异”落实到高质量样本、强对比测试和清晰的标注边界中。
